# Propwash FPV – landing page, roadmap and drone configurator

Static website for **Propwash FPV**, an FPV drone racing and freestyle mod for Minecraft 26.3
(Fabric and NeoForge), with an online drone configurator for the addon **Propwash: Just More Parts**.
This repository contains only the website, no mod source code.

## Structure

- `index.html` – the landing page (English and German, switchable), see [Landing page](#landing-page)
- `configurator/index.html` – the drone configurator (English and German, same switch)
- `docs/` – the documentation (propwashfpv.com/docs, English and German): overview, player guide, world rules
  (gamerules), add-on API, API reference and parts format; generated by `tools/build-docs.mjs`, never edited by hand
- `roadmap/index.html` – the roadmap (English and German, same switch), drawn from `assets/data/roadmap.json`
- `changelog/index.html` – the changelog of every release of Propwash FPV and Just More Parts (English and German, same
  switch), drawn from `assets/data/changelog.json`, which `tools/build-changelog.mjs` generates from the mods' `CHANGELOG.md`
- `impressum/index.html` and `datenschutz/index.html` – the legal notice and privacy policy required under German law
  (English and German, same switch), linked from the footer of every page; the bracketed placeholders need filling in
  before the site goes live
- `assets/css/style.css` – styles of all pages; `assets/css/configurator.css` – configurator only;
  `assets/css/docs.css` and `assets/js/docs.js` – docs only (menu, tables, code blocks with copy buttons);
  `assets/css/roadmap.css` – roadmap only; `assets/css/changelog.css` – changelog only
- `assets/js/main.js` – language switch, main navigation (menu button and Features menu), hero feed with pause switch, image switchers, video demo, gallery lightbox
- `assets/js/configurator/` – the configurator as plain ES modules:
  - core: `data.js` (catalog), `sharecode.js` (PW1 share codes and the entry point; `SHARE_FORMAT` chooses what new
    codes use), `sharecode2.js` + `sharecode2-tables.js` (the shorter PW2 codes), `crc32.js`, `inflate.js`, `tune.js`,
    `rules.js` (compatibility), `analysis.js` (flight analysis as in Propwash 0.5.2: energy balance, battery model and climb thrust), `fpv.js` (FPV camera rig and props in view),
    `tuning.js` (tune defaults and editing), `index.js`
  - page: `ui.js` (part pickers, paint, tune editor, OSD layer, stats, share code, import), `i18n.js` (texts),
    `assembly.js` (where every part sits on the drone), `paint.js` (paint tints), `viewer.js` (three.js viewer)
- `assets/js/roadmap/` – the roadmap page: `data.js` (loading, status counts and the validation shared with the test),
  `view.js` (horizons, release groups with progress rings, item cards)
- `assets/js/changelog/` – the changelog page: `data.js` (loading, the entries' inline Markdown and the validation shared
  with the test), `view.js` (filter, version list, release cards, copy link)
- `assets/data/roadmap.json` – what the roadmap shows (see [Roadmap](#roadmap))
- `assets/data/changelog.json` – what the changelog shows, generated (see [Changelog](#changelog))
- `assets/data/configurator/` – data from the Just More Parts web export: `catalog.json` (parts, presets, rules, paint,
  tune and share-code tables), `render.json` (frame layouts, motor seats, paint channels) and `models/` (one file per part:
  block-model geometry plus textures, loaded only for the parts on the drone)
- `assets/vendor/three/` – three.js r186 as a trimmed, minified bundle (MIT, `LICENSE`)
- `assets/vendor/pako/` – the deflate part of pako 2.1.0 (MIT, `LICENSE`), so share codes are byte-identical to the mod's
- `assets/img/` – real in-game screenshots as WebP (800 and 1600 px wide, plus cropped shots) and `og-image.jpg` for link
  previews, converted by `tools/build-landing-images.mjs` (see [Landing page](#landing-page)); `assets/img/docs/` – the
  pictures of the docs pages
- `sitemap.xml` and `robots.txt` – every page for search engines (see [Link check](#link-check))
- `assets/fonts/` – Saira and JetBrains Mono, both under the SIL Open Font License 1.1
- `tools/site-nav.mjs` – the main navigation and the footer links of every page, defined once (see
  [Navigation](#navigation))
- `tools/` – build and test scripts for the navigation, the landing page pictures, the configurator data and picture, the
  docs, the changelog, the roadmap check, the link check and the cache-busting stamps (`tools/stamp-assets.mjs`, see
  [Cache busting](#cache-busting); not needed at runtime)

No build step, no external requests, no cookies, no tracking. The chosen language and the hero's pause switch are
kept in the browser's `localStorage`; the drone built in the configurator lives only in the page address
(`configurator/#PW2…` or `#PW1-…`).

## Landing page

`index.html` is written by hand, English and German side by side (`<span lang="en">` / `<span lang="de">`, pictures
with `alt` and `data-de-alt`). It is for players who do not know Propwash yet; details live in the docs. Sections, in
this order (the ids are what the “Features” menu and older links use, so they stay):

| Section | id | Content |
| --- | --- | --- |
| Hero | `#top` | what it is, Download and the configurator as the two buttons, version line, rotating FPV feed |
| Get started | `#how` | four steps from building to racing, then the Flight School (`#learn`) for new pilots |
| Online configurator | `#configurator` | what the configurator does, its picture, the button to open it |
| What’s new | `#new` | three highlights of the latest feature release and its changelog link |
| Flight &amp; tuning | `#flight` | flight model, tuning, the in-game configurator, the four ways to fly |
| Video | `#video` | analog and digital video and how they break up (interactive) |
| Racing &amp; freestyle | `#racing` | race line, gates, ghost, spectating, tricks, course building |
| Survival | `#survival` | crafting, loot, batteries, wear and repair |
| More details | `#extras` | six tiles: lights, action cams, paint, sound and dust, bandos, a world that reacts |
| Screenshots | `#gallery` | pictures the page does not show elsewhere |
| FAQ | `#faq` | questions before the download |
| Download | `#download` (old: `#release`) | version, stores, compatibility, community (`#community`), add-on, source code (`#source`) |

A new feature gets a line or a tile in the section it belongs to, not a section of its own; what only matters for one
release goes into **What’s new** and moves into its section (or out) with the next release. For a release:

- **What’s new** (`#new`) gets the three highlights of the release with one picture each and links to
  `changelog/#propwash-<version>`; the version line in the hero names the release and links to `#new`; numbers such as
  tricks, lessons and world rules come from the mod's `CHANGELOG.md`
- the download section names the version, the add-on Just More Parts with its version and part count, and the
  compatibility lines of the changelog
- the pictures are the mod's own screenshots of the release commit:

```sh
node tools/build-landing-images.mjs --propwash <propwash repository>   # assets/img/*.webp and og-image.jpg
```

The list of pictures is `IMAGES` in that script: name, screenshot, widths and, for cut-outs, the crop in screenshot
pixels (windows are cut out at their real size, drone close-ups are cut around the drone because drones are shown at
their real size since 0.5.0). Pictures also used by the docs (`assets/img/docs/`) are not converted twice. After a
change of a window's layout in the mod, check the cut-outs by eye. Needs ImageMagick and `cwebp`.

The picture of the configurator section is the configurator itself (3D view and flight figures of the default preset,
English, standing still), taken in headless Chrome:

```sh
node tools/build-configurator-shot.mjs   # assets/img/configurator-preview-640.webp and -1200.webp
```

Run it again after the configurator or its default preset changes; `--code <share code>` shows another drone,
`--zoom <steps>` zooms in like the <kbd>+</kbd> key (default 2). Needs Google Chrome and `cwebp`.

## Navigation

The header of every page has the same navigation: a **Features** menu with the sections of the landing page (title and
one line each), **Docs**, **Changelog**, **Roadmap**, **Download** and the **Configurator** as the highlighted button;
Discord sits next to the language switch (in the small-screen menu as a link). The footer of every page has the same
link line. Both are defined once in `tools/site-nav.mjs`:

```sh
node tools/build-nav.mjs           # writes navigation and footer links into the hand-written pages
node tools/build-nav.mjs --check   # lists pages that are out of date, writes nothing
node tools/test-nav.mjs            # every page up to date, menu entries point to sections, old anchors still there
```

The docs pages take both from the same module when they are rendered (`node tools/build-docs.mjs --render-only`). A
new hand-written page goes into `HAND_PAGES` of `tools/build-nav.mjs`. Below 1100 px the navigation folds behind the
menu button; the width is in `assets/css/style.css` and `assets/js/main.js` and `test-nav.mjs` checks that both agree.
The Features menu opens on click, tap or keyboard (Escape closes it, focus returns to its button), without JavaScript
on hover and focus; without JavaScript narrow screens show the links as a row below the brand.

## Drone configurator

`configurator/` builds a drone from every Propwash and Just More Parts part:

- part pickers per category with search, a class filter (whoop, toothpick, cinewhoop, freestyle, race, long range,
  X-Class; video by link, accessories by mount), “only parts that fit”, fit badges and tips with pros, cons and what the
  part would change
- live flight figures like the workbench of Propwash 0.5.2 (weight, thrust-to-weight, hover throttle, top speed and its
  energy balance: flight times down to the landing voltage for mixed flying of the frame's class as the main value,
  aggressive/racing, hovering and cruising at the class's cruise speed, pack currents, landing voltage under load,
  base load of flight controller and video, motor temperature after 60 s full throttle and after a mixed flight) and
  the compatibility check (voltage, prop size vs. frame, battery fit, mounts, ESC and battery load)
- paint for every paint slot the build shows, like the paint screen in the game: the 16 dye colours, the 5 finishes
  (carbon, gunmetal, aluminium, gold, copper) and a custom colour; a swatch paints exactly its RGB value, as in the mod;
  “Randomize” paints all slots with a random but matching scheme (accent and partner colour, dark/light/metal base,
  props alike or front/rear for orientation)
- tune editor for rates (with a live rate-curve graph), PID, feedforward, TPA, filters and throttle curve (with graph),
  using the defaults the game derives from the build
- optional OSD layer (a Propwash OSD preset or the layout from an opened code)
- share code with copy button, share link and import field; opening a link or pasting a code loads the build and lists
  unknown parts
- 3D view with three.js: the parts' Minecraft block models, textures and paint tints placed like the mod's drone
  renderer (frame layouts, motor seats, camera tilt, accessory anchors); drag to turn, scroll or pinch to zoom,
  auto-rotate (off with reduced motion or paused animations), keyboard control on the canvas
- FPV camera preview (switch “3D / FPV camera” in the viewer, or open `configurator/?view=camera#PW1-…`): the image the
  drone's camera sends, drawn like the game's FPV view (since Propwash 0.4.0): 16:9 rectilinear from the lens with the drone's
  camera angle and the field of view of the camera in the video unit (`camera_fov_deg`, e.g. analog race 125°, digital
  lite 104°, HD 130°), the drone itself hidden except its props, spinning props as translucent blur discs in their paint
  colour, over a sky and grass backdrop; a camera-angle slider limited to the frame's camera mount (e.g. race 15–70°,
  freestyle 0–50°, as in the drone's service menu in the game) with the live props-in-view share – the angle is stored in
  the drone's tune and travels in the share code (PW1 revision 1.2) – the camera's field of view read-only, and toggles to
  mark the counted disc area, show still blades or draw the frame too
- screenshot menu in the 3D view: “Drone as PNG” (the drone alone, transparent, cropped, up to 1600 px, e.g. as the cover
  image of a forum post) and “Detail card” (1600 × 900 with name, class, key figures and share code); both are copied to
  the clipboard, or downloaded where the browser can’t copy images. Both always show the drone from the same angle,
  whatever the 3D view shows: from the front right and above (`SHOT_AZIMUTH` 34.75° from the nose towards the right
  side, `SHOT_ELEVATION` 27.75° in `viewer.js`), nose to the lower right, all four props in sight

### Updating the data

With a new web export of Just More Parts (default location: the newest `../propwash-justmoreparts/release/<version>/web-export`,
or pass `--export <dir>` / set `JMP_WEB_EXPORT`):

```sh
node tools/build-configurator-data.mjs     # catalog.json and the share-code test vectors
node tools/build-configurator-models.mjs   # render.json and models/
node tools/test-configurator.mjs           # share codes, presets, analysis, FPV camera and tune defaults against the export
node tools/test-configurator-render.mjs    # model files, paint tints, frame layouts, assembly and FPV prop hubs
```

`tools/fixtures/report-vectors.json` keeps share codes from bug reports with the build, analysis and FPV camera the
mod gives for them (hand-maintained, not overwritten by the build scripts); the test decodes, re-encodes and analyses
each one. The first is the 7″ deadcat whose props the game showed at the image edges while the old calculation said
0.0 %; its `game` entry holds what Propwash's self test counted in the rendered FPV image (2.01 % of 1708 × 960 pixels),
and the test fails if the configurator ever shows 0 % for it again. The same code carries the second report (flight
times and part stats a bit off, e.g. 24.2 min hovering and 124 °C at full throttle): `analysis` holds the figures of
Propwash 0.5.2 and Just More Parts 1.1.1 (19.6 min hovering, 11.9 min cruising, 8.1 min mixed, 5.8 min aggressive,
96 °C after 60 s full throttle), `analysis_before` the ones of an earlier pre-release build; the test checks that weight, thrust-to-weight, hover
throttle and props in view stay unchanged (the flight physics is bit-identical; the top speed moves with the climb thrust
of 0.5.0 and the battery model of 0.5.2) and that the energy figures changed.

Render definitions may carry a vanilla `transformation` (Just More Parts shrinks the X-Class frame models to fit
Minecraft's model limit and scales them back to real size this way); `build-configurator-models.mjs` bakes it into the
element coordinates, and the render test checks that every frame model reaches its motor positions.

`assets/vendor/three/three.min.js` contains only what the viewer imports (`tools/three-entry.js`). With `three` and
`esbuild` installed in a scratch folder:

## Documentation (`docs/`)

The docs pages describe one Propwash release and are rebuilt for every release from the Propwash source code:

```sh
# in the Propwash repository, on the release commit
tools/export_rules.sh                                        # build/web-export/gamerules.json
# here
node tools/build-docs.mjs --propwash <propwash repository> --images
node tools/test-docs.mjs
```

`--propwash` defaults to `PROPWASH_SRC` or the folder `propwash` next to this repository; `--gamerules <file>` points to
another export. `--images` converts the in-game screenshots the pages use (`docs/screenshots/` of the mod) to WebP in
`assets/img/docs/` (needs `cwebp`). `--version <x.y.z>` overrides the version from `gradle.properties` for a preview of
a release that is not versioned yet; the real release build runs without it. `--render-only` rebuilds the pages from
`tools/docs/data/` alone, without a Propwash checkout.

What comes from the code (`tools/docs/extract.mjs`, written to `tools/docs/data/*.json`):

- **world rules**: the mod's export of its rule catalogue (`tools/export_rules.sh`): ids, types, defaults, ranges,
  groups, value names, example commands and the same English and German texts as in the game; also published as
  `docs/gamerules/gamerules.json`
- **API reference**: every public type and member of `de.lardtom.propwash.api`, read from the Java sources
  (`tools/docs/java-api.mjs`), the API version and the types from outside the package that the API exposes
- **parts format**: the field names the part reader (`parts/PartJson.java`) reads per category, the enum values, the
  built-in mounts, parts and chemistries, and real part files as examples
- **keys and switch functions**: `KeyDefaults`, `SwitchFunction` and the language files
- **server.json**: settings, defaults and limits from `ServerRulesConfig`
- **versions**: mod, Minecraft, API, network protocol and parts format

The explanations are written in `tools/docs/pages/*.mjs` (English and German side by side). `tools/test-docs.mjs`
checks that the pages match the renderer, that every API type, part field, server setting and event has its
explanation (and none is left for something that is gone), that the API history covers the current API version, that
every example command is valid, and on every page: unique ids, working anchors and local links, English and German in
pairs, balanced tags, real umlauts in German, and no local paths or terms from the local denylist. When a release adds
something, the test names the file and the entry to write. The denylist is not part of this repository: the test reads
the same local file as the mod's public export (`PROPWASH_EXPORT_DENYLIST`, otherwise
`~/.config/propwash/public-export-denylist.txt`, one term per line) and fails without it.

The docs menu groups the pages under **Play** and **Make add-ons** (`GROUPS` and `PAGES` in `tools/docs/html.mjs`); the
overview page shows the same groups as cards. A new docs page needs four things: an entry in `PAGES` with its path, id,
group and title, a builder in `tools/docs/pages/<id>.mjs`, its line in `BUILDERS` of `tools/build-docs.mjs`, and a card in
`tools/docs/pages/index.mjs` (the build stops and names the page while the card is missing). A new group is one more
entry in `GROUPS`.

The header navigation and the footer links of the docs pages come from `tools/site-nav.mjs` (see
[Navigation](#navigation)); after changing them, run `node tools/build-docs.mjs --render-only` (`test-docs.mjs` fails
until then). The license note of the API page is `LICENSE_NOTE` in `tools/docs/pages/api.mjs`.

## Roadmap

`roadmap/` shows what is out, what is being built and what comes later – with rough horizons, never dates. The page
has no content of its own: `assets/js/roadmap/view.js` draws everything from `assets/data/roadmap.json`, so an update
only edits that file (no HTML).

```jsonc
{
  "schema": 1,
  "horizons": [                      // fixed order: released, now, next, later, ideas (a horizon may be left out)
    {
      "id": "now", "icon": "prop",
      "label": { "en": "Now", "de": "Jetzt" },                         // small coloured line above the heading
      "title": { "en": "In the next release", "de": "Im nächsten Update" },
      "intro": { "en": "…", "de": "…" },                               // optional
      "link":  { "href": "https://…", "label": { "en": "…", "de": "…" } }, // optional button under the intro
      "groups": [
        {
          "version": "0.5.0",                                           // optional; a release
          "title": { "en": "Learn, race, explore", "de": "…" },         // optional
          "items": [
            { "id": "world-rules", "icon": "globe", "status": "progress",
              "title": { "en": "World rules", "de": "Welt-Regeln" },
              "text":  { "en": "One line for players.", "de": "Eine Zeile für Spieler." },
              "link":  { "href": "…", "label": { "en": "…", "de": "…" } } }   // optional
          ]
        }
      ]
    }
  ]
}
```

- **Status:** `done`, `progress` (in progress), `planned` or `idea`. Items under `released` are all `done`, items under
  `ideas` are all `idea`, and `idea` appears nowhere else.
- **Progress:** a group with two or more items gets a ring with one segment per item (done green, in progress amber,
  planned blue) and “done of total” in the middle. The panel at the top of the page shows the first group with a
  `version` under `now`; the status counts and the jump links are counted from the file as well.
- **Releasing:** set the finished items of the release to `done`, move its group from `now` to the top of `released`
  (newest first – older releases then fold into one line), give it the link `../changelog/#propwash-<version>` (label
  “Full changelog” / “Alle Änderungen”), move the next group up from `next` to `now`, and run the check below.
- **Icons:** the names are the `ri-*` symbols in the sprite at the top of `roadmap/index.html` (16 × 16, drawn with
  strokes like the configurator's icons). A new icon is a new `<symbol id="ri-…">` there.
- **Texts:** short and player-facing (title up to 48, text up to 130 characters), both languages, no HTML, no dates
  (years, quarters and month names are rejected).

```sh
node tools/test-roadmap.mjs   # validates roadmap.json, the icons, and that every page links to the roadmap
```

## Changelog

`changelog/` lists every release of Propwash FPV and Propwash: Just More Parts point by point, newest first: title line,
highlights, then New, Improved, Fixed, Compatibility and Known issues. A switch shows both or one of them, the version
list links every release, and each release has a fixed anchor for roadmap cards and Discord posts:
`changelog/#propwash-0.4.0`, `changelog/#jmp-1.0.0`, `changelog/#propwash` / `changelog/#jmp` for a whole product.

Nothing on the page is written by hand. `tools/build-changelog.mjs` reads the player-facing `CHANGELOG.md` of both mods
from git – by default at the newest release tag `v<x.y.z>`, so notes of an untagged release never show – and writes
`assets/data/changelog.json`:

```sh
# after tagging a release of Propwash or Just More Parts
node tools/build-changelog.mjs                   # writes assets/data/changelog.json, lists entries without German text
node tools/build-changelog.mjs --add-missing     # adds those entries to tools/changelog/de.json with an empty value
node tools/test-changelog.mjs
```

The repositories default to `PROPWASH_SRC` / `JMP_SRC`, otherwise `propwash` and `propwash-justmoreparts` next to this
repository (or next to its main checkout when you work in a worktree); `--propwash <dir>`, `--jmp <dir>`,
`--propwash-ref <ref>` and `--jmp-ref <ref>` override them, `--check` only reports whether the JSON is up to date.

`CHANGELOG.md` format: `## [x.y.z] — Title` per release (`## [Unreleased]` and other non-version headings are skipped),
`### Highlights|New|Improved|Fixed|Compatibility|Known issues` and `- ` bullets with `**bold**`, `*emphasis*`, `` `code` ``
and `[links](https://…)`. Anything else inside a release stops the build and names the line. Highlights start with their
name in bold (`**Flight training:** …`); the page shows that name as the card title.

German: the changelogs are English, the German texts live in `tools/changelog/de.json` – per product and version, the
English source line as key and its German text as value. A line repeated word for word in a later release reuses its
translation. `test-changelog.mjs` fails while an entry has no German text, while a German text is no longer used (after a
line changed), when the JSON differs from a fresh build or a newer release tag exists, and checks the navigation and footer
links of every page and that the released groups of the roadmap link to `../changelog/#propwash-<version>`.

## Link check

```sh
node tools/test-links.mjs                 # every local link, anchor, picture, canonical address, sitemap, unused pictures
node tools/test-links.mjs --external      # also lists every external address and the pages that use it
node tools/test-links.mjs --online        # also requests each external address and prints the answer
node tools/test-links.mjs --write-sitemap # rewrites sitemap.xml after adding or removing a page
```

All local links are relative, so the pages also work under a sub-path. The anchors the changelog draws from its data
(`#propwash-0.5.0`, `#jmp-1.1.0`, …) count as present. Addresses that only work once a release is published – the
public source repositories on GitHub (`https://github.com/LardTom/propwash-fpv`,
`https://github.com/LardTom/propwash-justmoreparts`) and the Modrinth page in review – are listed under `PENDING` in the
script and marked “after publishing” in the list. The source repositories are named in one place per page type:
`SOURCE` in `tools/site-nav.mjs` (footer of every page), `SOURCE_JMP` in `tools/docs/html.mjs` (docs), the download
section and the FAQ of `index.html`, and the roadmap card “Source code goes public”.

## Cache busting

GitHub Pages serves this site with `max-age=600` caching. Without cache busting, a browser that already cached
`assets/css/style.css` or a configurator script keeps using that cached file for up to 10 minutes after a new HTML
page of the same release has already loaded – new tiles get squeezed, the footer wraps one word per line, until a
hard reload. `tools/stamp-assets.mjs` fixes this by giving every local reference to `assets/css/*.css` and
`assets/js/**/*.js` a version query derived from the content it currently points to, e.g. `style.css?v=a1b2c3d4` (8
hex characters of a sha-256 of the file): a page always pulls the exact CSS/JS that was live when it was generated,
whatever a browser still has cached under the old, unversioned or differently stamped URL.

```sh
node tools/stamp-assets.mjs          # restamp every page and script that is out of date
node tools/stamp-assets.mjs --check  # report what is out of date and exit 1, writes nothing (used by the test below)
node tools/test-stamp-assets.mjs     # every local css/js reference, on every page and between the scripts, carries the current hash
```

Stamped: every `<link rel="stylesheet">`, `<link rel="modulepreload">` and `<script src>`/`<script type="module"
src>` of a local `assets/css/*.css` or `assets/js/**/*.js` file, on every page including the ones
`tools/build-docs.mjs` generates – and the ES module imports *between* the configurator's own scripts (`import …
from './data.js'`, the dynamic `import('./viewer.js')` the 3D view uses, and the changelog's and roadmap's `view.js`
→ `data.js`). That last part matters because the configurator and the roadmap/changelog pages are themselves ES
modules that import several sibling scripts directly – a stale cached `data.js` loaded alongside a fresh `ui.js`
would be exactly the same kind of broken-layout bug, just inside the configurator instead of on the page. A script's
hash also changes whenever a module it imports changes (computed in dependency order, so the one import cycle in the
configurator – `sharecode.js` and `sharecode2.js` import each other – gets one shared hash for both instead of an
unsolvable loop), so editing `rules.js` alone still busts every page that eventually loads it through `ui.js`.
Imports of `assets/vendor/*` (three.js, pako) are left alone: out of scope, pinned and only touched by the rebuild
command further up.

`tools/build-docs.mjs` calls the same stamping step right after writing `docs/**/index.html`, so regenerated docs
pages keep current stamps without an extra step. After hand-editing any other HTML page or any CSS/JS file, rerun
`node tools/stamp-assets.mjs` before committing; `tools/test-stamp-assets.mjs` (part of the test suite) fails with
the list of files to restamp until you do. `tools/test-links.mjs` and the other tests already ignore the `?v=` query
when resolving a local reference.

## Publish on GitHub Pages

Before a release goes live: publish the public source repositories first (the pages link to them), upload the mod
files, then merge the release branch into `main` and push. `node tools/test-links.mjs --online` then shows every
external address answering.

1. Push this folder to the repository `LardTom/propwash`.
2. Settings → Pages → Build and deployment → Source: *Deploy from a branch*, branch `main`, folder `/ (root)`.
3. `.nojekyll` is included, so the files are served exactly as they are.

All paths are relative, so the pages work from the custom domain `https://propwashfpv.com/` (fallback `https://lardtom.github.io/propwash/`), the configurator
from `https://propwashfpv.com/configurator/`, the roadmap from `https://propwashfpv.com/roadmap/`, the changelog from
`https://propwashfpv.com/changelog/`.

## Link previews

`og:image` and `twitter:image` need an absolute URL. They point to
`https://propwashfpv.com/assets/img/og-image.jpg`. With a different repository name (or a custom domain),
change the URLs in the `<head>` of `index.html`, `configurator/index.html`, `roadmap/index.html` and `changelog/index.html`,
`SITE` in `tools/docs/html.mjs` and `tools/test-links.mjs`, and `sitemap.xml` / `robots.txt`. Every page also carries its
canonical address and `og:url`.
